# 可选项目运行层

先解析 `ASM_CONFIG` 与 vault，再检查 `00-系统/投资运行配置.json`。文件不存在就沿用原技能；文件存在但不是 JSON 对象、路径越出 vault 或必要资源缺失时，明确报告扩展未完成，不猜测合同或账本，不阻断不依赖它的只读分析。不得通过建立空文件掩盖坏配置。

## 连续研究

`workflow: astra_full_v1` 时，先读配置的 `contract`，再读 [完整研究流程](astra-workflow.md)。它要求当前实际模型在 `allowed_models` 中，并在同轮完成机械池、催化核查、正式取舍和反方复核；用户明确只要机械扫描时保留「候选池，未提名」。同模型自检和接续其他模型旧结论都不能标成跨模型独立验证。

决策前运行 `scripts/decision_journal.py status`，写回前 `append` 并 `validate`。记录主题、载体与当前行动，维护同主题同模式的连续链，改判必须引用先前条件、新事件或用户真实指示。账本里的 enter/exit 是研究或建议状态，绝不等于委托或真实成交。新增的写入范围仅为用户配置并已授权的账本；前后快照、逐文件暂存和同轮提交仍然适用。

数据结构见 [连续决策账本](decision-journal.md)，研究对照见 [影子对照](shadow-comparison.md)。`scripts/system_check.py --vault <vault>` 只检查配置、记录和可选文件指纹；通过不证明模型身份或盈利能力。安装器不启用该层，也不复制作者的合同、记录或私有数据。启用方法在仓库 `docs/研究运行层.md`。

## 项目自行提供的 decision_ops

只有配置含 `decision_ops` 时，才读其合同与脚本。该适配器不是本仓库内置能力，使用者须自行提供；`contract/script/calendar/candidates/actions/outcomes` 均为 vault 内相对路径。调用前检查文件和授权，按项目合同执行，不从作者机器寻找实现。

- 该模式下「跟」只登记研究跟踪，明确「立项／跟并立项」才建页、筛载体；默认模式原有触发不变。
- 明确取舍的候选追加到 candidates，行动及状态变化追加到 actions，保留来源、复核期限和前序决定。不将到期视为已执行或撤销，不自行解除用户不重评的指示。
- 复盘执行配置脚本的 `daily --vault <vault> --as-of <数据日>`，读取结果，将到期待核实事项放入④区。候选 T+5/10/20 以真实交易日定点，缺数不顺延，历史导入只作诊断。
- 宽度仍双源校验。只有 `breadth` 返回 `locate:false`，且人工确认其他决策不受影响时，才省逐股定位；未知配置保守排查，不套 ST 容差。
- 配置中的候选、行动、结果及日历文件只有得到当前项目写入授权后才加入白名单；每个文件单独暂存。不为通过门槛反复扫描同输入，不改变纪律、预注册条件或规则冻结。

只配置 decision_ops 而未选择 astra_full_v1 时，仍可按其合同使用该适配器；不要因此运行仅支持 Astra 配置的 system_check。缺少该扩展时明确缺口，不声称候选回填或行动到期处理已完成。
